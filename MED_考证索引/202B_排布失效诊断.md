# Event 202B 排布切换失效 · 诊断报告

> **现象**：202B 画布上「排布：方形 ⇄」按钮点不动——方形与横排看起来一样，无法切换。
> **结论**：**不是画布尺寸的问题，画布数据完全正常**。是插件（`med-layout-toggle`）的**深度分层算法在有环图上失效**，导致 174 个节点里有 **123 个被判为"深度 0"**，全部竖着堆成一列。
> **诊断日期**：2026-10-01｜**方式**：只读。**未改动任何文件**（画布与插件均原样）。
> **诊断手段**：直接 `require` 插件的 `__test` 接口（`graphInfo` / `applyLayout` / `detectMode` / `squareMetrics`），用**插件自己的算法**跑真实数据。

## 一 根因链（四步）

### ① 画布本身没有问题

| 检查 | 结果 |
|---|---|
| 节点／连线 | 174 / 187 |
| 悬空连线（两端有一端不存在） | **0** |
| Entry 出边 | 正常（`n_entry → n0`） |
| 从 Entry 可达 | **166 / 174** |
| 孤立无上游 | 仅 2 个（`n_entry` 正常；`n39` 是真断点，见 §四） |

### ② 深度分层被一个"环"卡住

插件用 **Tarjan 缩点 + Kahn 拓扑松弛**算深度（`main.js` 152–199 行）。202B 里存在一个 **8 节点环**：

```
n170 [Choice] ──→ n15 [Content] ──→ n174 [Dialog] ──┐
     ↑                                              │
     └──────────────────────────────────────────────┘
     │
     ├──→ n176 → n177 → n178 → n179 [Choice] → n180 ──┘
```

- `n170` 的两个选项分支**又绕回自己**（`n15→n174→n170`、`n176→n177→n178→n179→n180→n170`）
- 环上节点入边：`n170` 3 条、`n15` 1 条、`n174` 1 条、`n180` 1 条
- **Kahn 松弛需要某强连通分量的入度降到 0 才会入队**；这个环已经收了 `n14` 的入边，却因为自身成环而**永远不会被出队**

### ③ 130 个分量拿不到深度 → 兜底成 0

| 指标 | 数值 |
|---|---|
| SCC 总数 | 167（root 所在 SCC 仅 1 个节点） |
| Kahn **实际处理**的 SCC | **36 / 167** |
| **未赋深度**的 SCC | **130 个**（合计 130 节点） |
| 环正向可达节点 | **159 / 174** ← 几乎所有节点都在环的下游 |
| 能到达环的节点 | 15 |

而 `main.js:195` 是这句兜底：

```js
const d = sccDepth.get(sccOf.get(n.id));
depth.set(n.id, d === undefined ? 0 : d);   // ← 拿不到深度就当成 0
```

于是 **123 个节点全被压到深度 0**。

### ④ 深度 0 的 123 个节点被"竖着堆"

`placeRow()`（`main.js:232–239`）对**同一深度**的节点是这样排的：

```js
for (const n of g.byDepth.get(d)) { n.x = x.get(d); n.y = cy; cy += b.h + o.gapY; }
```

**同深度的节点只有一个 x、y 逐张往下堆**。123 张卡堆一列 → 横排排出来是一根**高 25116px 的竖条**，与"方形"在观感上没有区别。

**两种模式都排成了竖条**（比例 0.84 / 0.34），所以看起来"切不动"。

### 按钮为什么像"失灵"

插件的判定是 `长宽比 ≥ 2.5 → 横排，否则方形`（`main.js:381`）。于是形成死循环：

```
文件是方形(0.84) → 点按钮 → 切成横排 → 排出来仍是竖条(0.84)
   → detectMode 判为 square → 按钮仍显示「排布：方形」→ 再点，重复
```

**按钮文字永远不变**，因为文件**永远回不到横排状态**。这正是"无法切换"的观感来源。

## 三 两条修法（互相独立，可只做一条）

### 方案 A（推荐·治本）修插件的深度计算

问题出在 Kahn 松弛**遇到环就静默停摆**。改成"缩点图上求最长路径、允许环内节点同层"即可：

```js
// main.js 181-189 行现写法：ind[w] 降到 0 才入队 —— 环上分量永远等不到
// 改为：不做入度门控，直接在缩点图上按"从 root 出发的最大深度"迭代到收敛
const sccDepth = new Map([[rootScc, 0]]);
const dq = [rootScc];
while (dq.length) {
  const u = dq.shift();
  const want = sccDepth.get(u) + 1;
  for (const w of succ[u]) {
    if ((sccDepth.get(w) ?? -1) < want) { sccDepth.set(w, want); dq.push(w); }  // ← 不看入度
  }
}
```

- 缩点图是 **DAG**，上式必收敛；环内节点（同一个 SCC）本就该同层，与代码注释里"环内部节点同层"的设计意图一致
- 影响面：只改深度赋值，不动坐标、不动合并、不动正文
- **务必先在 `tools/ncanvas_layout.ps1` 与插件间做等价性回归**（README 声明两者坐标逐点一致，改一处要同步）

### 方案 B（治标·改稿）打断脚本里的回环

把 `n170` 的选项支从"绕回 `n170`"改为"汇入下一段"，让图彻底无环。代价是**改别人的剧本结构**——按边界规则须先给 diff 预览、经作者同意。

> 若暂不动脚本，也可临时用命令面板的 **`排布设为横排`** 强制排一次；但因为深度分层已经坏了，**排出来仍是竖条**——所以方案 A 才是真解。

## 四 顺带发现（与本次故障无关，但建议处理）

**`n39` 是个断点**：`n39`（老韩：「整点猫尿，欺负个孩子，脸上有光？…」）**没有任何入边**，导致 `n39 → n40 → n41 … n46` 这 8 个节点**从 Entry 不可达**。

- 但 `audit_flow` 之前报过"全部文件通顺"，说明这个断点在检出范围之外——**建议核一下 `n38` 附近是不是漏了一根连线**
